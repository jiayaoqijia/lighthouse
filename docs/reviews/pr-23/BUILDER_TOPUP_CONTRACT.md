# Builder top-up validity contract

Use the current detailed consensus transition in [consensus-specs d2021d27](https://github.com/ethereum/consensus-specs/blob/d2021d2719235f0df4726a1d330502cb15aa8ea3/specs/gloas/beacon-chain.md). The builder withdrawal-credential prefix is a common validity precondition before registry lookup, including existing-builder top-ups. A valid-prefix existing-builder top-up does not reauthenticate registration, change the stored execution address, or require the original registration signature. Invalid prefixes do not credit the builder. The EL must still execute its ordinary request contract and transport successful request bytes; it does not substitute a local stake registry for the CL.

The EIP-8282 prose can be read as ignoring the entire credential value for top-ups. Existing upstream [EIPs PR #12572](https://github.com/ethereum/EIPs/pull/12572), head `033b4e91766c006e3871fc362e7a31d19a2f2dce`, explicitly clarifies the prefix precondition and locked principal. It was still open/unmerged when checked. This records the compatibility rule implemented by both clients and the detailed reference, and does not treat the unmerged prose amendment as a new adopted protocol revision.

Actual client and unchanged current Python reference probes in [ETH2030 PR #160](https://github.com/alt-research/eth2030/pull/160) use the same authenticated registered-builder state, 1 ETH and zero signature. Prefix `0xb0` credits exactly 1 ETH; changing only the prefix to `0xff` credits zero. Neither changes the recipient. This local contract is resolved without a unilateral consensus change; upstream prose reconciliation remains an external dependency.
